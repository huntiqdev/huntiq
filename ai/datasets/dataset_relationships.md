# HUNTIQ Dataset Relationships

**Project:** HUNTIQ Marketplace AI Platform  
**Purpose:** Formal relationship catalog defining data flows, label alignments, and joint training interactions among the 30 dataset modules.  
**Version:** 1.5.0 (Audited Architecture)  

---

## 1. Coordinated Intelligence Philosophy

The HUNTIQ AI system does not operate as 30 siloed, disconnected models. Instead, the 30 dataset modules serve as specialized knowledge packages for a unified conversational intelligence architecture.

Every incoming user message traverses a coordinated path where:
1. Lexical representations and language identifiers are established uniformly ([Module 14](file:///home/poven/GO%20PROJECT/sellbuy/ai/datasets/14_multilingual_understanding) & [Module 15](file:///home/poven/GO%20PROJECT/sellbuy/ai/datasets/15_spelling_noisy_input)).
2. Conversational greetings and platform boundaries are recognized early ([Module 01](file:///home/poven/GO%20PROJECT/sellbuy/ai/datasets/01_general_greetings), [Module 02](file:///home/poven/GO%20PROJECT/sellbuy/ai/datasets/02_identity_assistant_behavior), [Module 04](file:///home/poven/GO%20PROJECT/sellbuy/ai/datasets/04_domain_classification)).
3. Marketplace semantics (intent, category, entities, prices, locations) are extracted into canonical JSON structures ([Modules 05, 06, 07, 08, 09, 10](file:///home/poven/GO%20PROJECT/sellbuy/ai/datasets/)).
4. Dialogue state, constraints, follow-ups, and user preferences are maintained continuously across multi-turn sessions ([Modules 11, 12, 13, 21, 22, 23, 24, 26, 27](file:///home/poven/GO%20PROJECT/sellbuy/ai/datasets/)).
5. Authorized backend operations are proposed to the sovereign Go backend for database lookup ([Module 19](file:///home/poven/GO%20PROJECT/sellbuy/ai/datasets/19_tool_calling_structured_outputs)).
6. Database results are verified, grounded, and translated into concise, natural responses in the user's native language ([Modules 03, 16, 20, 25, 28, 29, 30](file:///home/poven/GO%20PROJECT/sellbuy/ai/datasets/)).

## 2. Key Architectural Couplings

### A. Intent & Category Coupling (Modules 05 & 06)
- **Shared Ontology:** When Module 05 classifies an intent as `marketplace_search` or `property_discovery`, Module 06 immediately constrains category candidates using the live PostgreSQL taxonomy hierarchy (e.g., `real-estate` -> `apartments` -> `for-rent`).
- **Conflict Prevention:** If Module 05 detects a non-commercial intent (e.g., `social_greeting` or `platform_support`), category extraction is bypassed to prevent phantom database searches.

### B. Entity, Price & Location Synergy (Modules 07, 09 & 10)
- **Canonical Normalization:** Text expressions like "35k birr" or "35 ሺህ ብር" are converted by Module 09 into `{"max_price": 35000, "currency": "ETB"}`.
- **Geographic Anchoring:** Module 10 resolves local aliases (e.g., "Megenagna", "Bole Michael", "Piassa", "Finfinnee") into canonical subcity, woreda, and city identifiers matching the Go backend geocoding authority.
- **Specification Structuring:** Module 07 parses domain-specific specs (bedrooms, storage, brand, vehicle transmission) and binds them to the active search schema.

### C. Dialogue Context & Follow-Up Persistence (Modules 13, 22, 26 & 27)
- **Slot Inheritance:** When a user says "Make that under 25,000 birr" (Module 13), Module 22 inherits the previously selected category and location from dialogue state while updating only the budget slot.
- **Context Hygiene:** When Module 26 detects an explicit category switch ("Actually show me cars instead"), all property-specific slots (bedrooms, furnishing, rental period) are flushed, preventing cross-domain pollution.

### D. Safety, Authorization & Tool Gateway (Modules 18 & 19 -> Go Backend)
- **Zero Hallucination Bridge:** Python never executes raw SQL or database mutations.
- **Strict Authorization:** Module 19 produces strictly typed, schema-compliant tool proposals. The Go backend inspects the user's session, authenticates the request, verifies permissions, and executes the query against PostgreSQL.
- **Security Guardrails:** Module 18 inspects both incoming user inputs and outgoing tool arguments for prompt injection, prohibited goods, and unauthorized administrative actions.

### E. Grounding & Natural Response Generation (Modules 20 & 30)
- **Truth Anchoring:** Responses generated by Module 30 must be strictly grounded in the verified JSON results returned by Go (Module 20).
- **Anti-Hallucination Rule:** If the database returns 0 listings, Module 30 must explicitly state that no matching items were found and suggest relaxing specific constraints (Module 27), rather than inventing synthetic listings.
- **Multilingual Parity:** Natural responses in English, Amharic, Afaan Oromoo, and Tigrinya preserve identical factual constraints, pricing, and contact guidelines.
